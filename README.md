# Arch Linux Workstation Install

```
LUKS2 (FIDO2 PIN + touch) → Btrfs subvolumes → signed UKIs, Secure Boot with the machine's own keys → snapper + snap-pac + snap-restore → Sway (Wayland) + Quickshell → AppArmor + Firejail + ufw + hardened sysctl → YubiKey (FIDO2 + OpenPGP)
```

- `install.sh` - live ISO. Partition, encrypt, FIDO2 LUKS enrollment, pacstrap, base config (tty1 runs `login` for your user, so a boot is LUKS, then a YubiKey touch, or the password with the key unplugged), Secure Boot keys (created, both UKIs signed), clone this repo, keys enrolled when the firmware is in Setup Mode, reboot. Prompts: disk (the ISO's own stick and empty card readers are not offered), timezone (a canonical `zone.tab` name, aliases are rejected: the Wi-Fi regulatory domain comes from its country; `UTC` and `Etc/*` pass and set none), username, three passwords. Log: `/root/arch-install.log`, copied to `/var/log/arch-install.log` on the installed system. Run from a checkout (`post-install.sh` and `.git` next to it) and it installs that tree instead of cloning `master`.
- `post-install.sh` - installed system, first boot. Boot entry cleanup, Wi-Fi when offline, NM connectivity interval, snapper limits, LUKS header backup to a USB stick, pacman hooks (reboot-required flag, orphan report, pacnew list, launcher app-list refresh), Intel GPU PMU helper, battery charge limit, YubiKey PAM (login, sudo, polkit, lock screen), lid and power-key policy, yay (AUR helper for `slack-desktop`, `zoom`; built with `bin/yay-git`, which falls back to the GitHub AUR mirror when aur.archlinux.org is down - `yay-git slack-desktop zoom` works without yay too), LibreWolf (firejail XDG whitelist + overrides), firecfg symlinks for the installed programs `firecfg.config` names, web apps (Brave Origin from the AUR, jailed like LibreWolf), dotfiles symlinks, GTK/Qt theme (adw-gtk3 + qt6ct), key import, GPG/SSH, an optional SMB share (systemd automount). Resumable via done-markers.

Prerequisite: both YubiKeys provisioned per [YUBIKEY.md](./YUBIKEY.md) (GPG identity on card, the same FIDO2 PIN set on both).

## Step 0 - Firmware, ISO

Firmware setup, once (F1 at power-on on a ThinkPad), in this order:

1. **Security → Password → Supervisor Password**: set one, store it in the password manager. It is what keeps someone with the device from turning Secure Boot off or resetting its keys. It survives BIOS flashes; lost, the firmware setup is shut for good while the machine keeps booting.
2. **Security → Secure Boot**: `Secure Boot` **On**, then **Reset to Setup Mode** (not Clear All Secure Boot Keys, not Restore Factory Keys). Setup Mode means no Platform Key: the firmware takes new keys and verifies nothing until it has them, so the unsigned ISO boots and `install.sh` enrolls the machine's own keys (Step 1). With the toggle already On, the first boot after enrollment enforces.
3. **Security → Security Chip**: on (the default). `sbctl enroll-keys` reads the TPM's event log for the option ROMs the firmware ran (hardware the new keys would lock out) and refuses without one: keys made, UKIs signed, nothing enrolled until the chip is on and `sudo sbctl enroll-keys -i` runs. `install.sh` says so before its prompts.

Download ISO + `sha256sums.txt` from [archlinux.org/download](https://archlinux.org/download/).

```sh
sha256sum archlinux-x86_64.iso        # Linux
shasum -a 256 archlinux-x86_64.iso    # macOS
```

macOS:

```sh
diskutil list                                                         # find USB by size
diskutil unmountDisk /dev/disk4                                       # unmount, not eject
sudo dd if=archlinux-x86_64.iso of=/dev/rdisk4 bs=4m status=progress  # rdisk = raw node; lowercase 4m
diskutil eject /dev/disk4
```

Linux:

```sh
lsblk
sudo umount /dev/sdb*                                                 # "not mounted" is fine
sudo dd if=archlinux-x86_64.iso of=/dev/sdb bs=4M status=progress oflag=sync   # whole device, not sdb1
sync && sudo eject /dev/sdb
```

- macOS `diskutil list` afterwards shows `FDisk_partition_scheme` + small `0xEF` + free space - normal, write succeeded.
- Won't boot (`Secure Boot Violation`, or straight back into the firmware): Secure Boot is enforcing with keys that did not sign the ISO. Reset to Setup Mode (above) for an install; Secure Boot Off for that boot when the installed system is to be kept (Recovery), or the signed stick (Recovery stick). Pick the `UEFI:` entry, not Legacy.

## Step 1 - `install.sh` (live ISO)

Get online first. Wired = automatic. Wi-Fi:

```bash
iwctl device list                       # station name, e.g. wlan0
iwctl station wlan0 scan
iwctl station wlan0 get-networks
iwctl station wlan0 connect "<SSID>"    # prompts passphrase; install.sh copies WPA-PSK profiles (hidden flag included) into the installed system, nothing else
```

```bash
curl -fsSL https://raw.githubusercontent.com/philipp-bliznuk/arch-btw/master/install.sh -o install.sh
bash install.sh                         # not curl | bash - needs a tty for prompts
```

Before any prompt the script waits for the ISO's keyring (`pacman-init.service`, which waits for the clock to sync; 5 min at most), refreshes it and resolves the whole package list against the repositories (`pacman -Sp`), so a stale ISO or a renamed package fails here, with nothing wiped yet. Prompts, in order: disk (wiped), timezone (`Europe/Berlin`), username, LUKS passphrase, user password, root password (each twice). Summary → type `YES`. Its `Secure Boot` line reads the firmware: `Setup Mode - own keys enrolled`, `not in Setup Mode - UKIs signed, enroll later`, or `no TPM event log - UKIs signed, enroll later` (Step 0, item 3; the command is under Recovery). An enforcing firmware stops the script before the prompts: the new keys could never get in.

FIDO2 enrollment pauses twice, right after `YES` (disk wiped and LUKS formatted, before pacstrap): `Insert YubiKey #1 ONLY (remove the other), then Enter`, then key #2.

- Exactly one key inserted per pause (`--fido2-device=auto`).
- Each key asks **FIDO2 PIN + touch**. That is the PIN from `ykman fido access change-pin`, not the OpenPGP PIN; the prompt prints the retries left. Three wrong in a row block the applet until replug, eight in total wipe it ([YUBIKEY.md](./YUBIKEY.md#pins)).
- Every boot asks the same PIN + touch (`--fido2-with-client-pin=yes`): laptop and key stolen together stay shut.
- Enrollment failure → retry prompt, not abort; `s` at that prompt goes on without that key (a key that will not enroll, or only one at hand). With no key enrolled the passphrase unlocks and the script says how to enroll later (YUBIKEY.md, Recovery).
- Boot with no key inserted → passphrase prompt after 30 s. Keyslot 0 always works.

Flags: `--skip-fido2` (VM), `DEBUG=1 bash install.sh` (trace). Re-run after failure re-wipes the disk (after unmounting `/mnt` and closing `cryptroot` from the last run; a mapping that stays open, a shell left inside `/mnt` say, stops the script before the wipe); the Secure Boot keys are enrolled as the installer's last act, after every step that can ask for a re-run, so the firmware is still in Setup Mode for it (once the keys are in, the ISO boots with Secure Boot Off for that boot, and a re-run needs another Reset to Setup Mode: Recovery).

Baked in: `sgdisk` 2G ESP (mounted at `/boot/efi`, `umask=0077`) + LUKS2 remainder; Btrfs `@ @home @snapshots @swap` (`noatime,compress=zstd`; btrfs takes `compress=` from the first mount for the whole filesystem, `genfstab` writes it for `/swap` too, and the swapfile is NOCOW from `btrfs filesystem mkswapfile`, which compression never touches; a subvolume of its own because btrfs cannot snapshot one holding an active swapfile); hostname `arch-btw`; locale `en_US.UTF-8`, keymap `us`; RAM-sized hibernation swapfile; systemd HOOKS, two UKIs and no boot loader (`EFI/Linux/arch-linux.efi` behind the firmware entry `Arch Linux`, the default; the LTS one as `EFI/BOOT/BOOTX64.EFI`, the removable-media path a firmware tries with no entries at all, F12 → `Arch Linux LTS`; nothing between firmware and kernel to configure, verify or edit; no fallback images: the LTS kernel covers a kernel regression, while both UKIs share `mkinitcpio.conf` and rebuild in the same pacman transaction, so a broken initramfs is the ISO case under Recovery); Secure Boot with the machine's own keys (`sbctl create-keys` into `/var/lib/sbctl/keys`, both UKIs signed and tracked, `sbctl enroll-keys -i` while the firmware is in Setup Mode: PK, KEK and db hold one certificate each, Microsoft's are not enrolled, dbx is kept; from then on mkinitcpio's `sbctl` post hook signs every UKI it builds, `sbctl verify` lists the ESP); ufw on (INPUT DROP, OUTPUT ACCEPT); hardened sysctl; Quad9 DoT (both addresses, strict; `Domains=~.` sends every name there, the link's resolver is asked only for names under a DHCP search domain and over TLS as well, so LAN names resolve only from a router that speaks DoT; a captive portal that blocks port 853 leaves NM at `limited` rather than `portal` and nothing resolves until the portal is passed: `sudo resolvectl dnsovertls wlpXs0 no && sudo resolvectl domain wlpXs0 '~.'` lets the LAN resolver answer alongside Quad9; `sudo resolvectl revert wlpXs0` or the next reconnect undoes it); Cloudflare NTS; `earlyoom` (`systemd-oomd` acts only on units that opt in with `ManagedOOMMemoryPressure=`, none do here; earlyoom watches free RAM and swap and SIGTERMs the largest process when both are nearly gone, browser content processes first, sway and quickshell last (`--prefer`/`--avoid` move oom_score by 300): `/etc/default/earlyoom`); Wi-Fi regulatory domain from the timezone's country (`wireless-regdb`, `/etc/conf.d/wireless-regdom`, applied by udev at boot; Intel LAR firmware is `self-managed` and takes the country from the AP, the global domain covers adapters without that); `kernel-modules-hook`; `udisks2` (`udisksctl mount -b /dev/sdX1` as the user, or the launcher's Utils → USB: polkit's default lets an active local session mount, unlock LUKS and power off removable drives without a prompt, nothing automounts; `/etc/polkit-1/rules.d/10-udisks2.rules` puts `loop-setup` and `modify-device` behind an admin auth, since mounting a file one wrote hands root's filesystem parsers to its author); `imv` and `mpv` as the image and video handlers for `xdg-open` (LibreWolf registers neither; Setup → Default apps picks); journald 200M; JetBrainsMono Nerd Font; ucode auto (Intel/AMD); repo cloned to `~/projects/dotfiles` (a failed clone is a warning with the command for the first boot, not a re-run: the system is installed by then). `btop`, `fastfetch`, `tree`, `go-yq`, `bun` are for the human at the prompt, nothing in the repo calls them. Lid policy: post-install step `lid`.

## Step 2 - `post-install.sh` (first boot)

Unlock, then `Ctrl-Alt-F2` → log in on **TTY2** (TTY1 would `exec sway` once the dotfiles are linked; until step 9 every VT asks the password only).

```bash
~/projects/dotfiles/post-install.sh              # run / resume
~/projects/dotfiles/post-install.sh --list       # step status
~/projects/dotfiles/post-install.sh --redo keys  # force one step
```

Runs as user, `sudo` where needed. Markers: `~/.local/state/arch-btw/done/`. Log: `~/.local/state/arch-btw/post-install.log`.

```
keys/gpg/pb/public.asc   keys/gpg/pb/secret-keys.asc
keys/gpg/gx/public.asc   keys/gpg/gx/secret-keys.asc

keys/ssh/id_ed25519_gx   keys/ssh/id_ed25519_gx.pub
```

`ic` = card identity (SSH key exported from card). `pb`/`gx` = on-disk. Git signing config comes from dotfiles `git/{pb,ic,gx}`, not the script: `git/config` includes one of them per remote (`includeIf "hasconfig:remote.*.url:git@pb:**/**"` and so on), so a repo's identity follows where it pushes; with remotes on two of the hosts (a fork: `origin` on gx, `upstream` on pb) the include later in the file wins, gx, whatever the remote order, and a repo whose remotes match none has no identity, where `user.useConfigOnly` makes git refuse the commit instead of guessing one (GECOS as the name, login and host as the email; with GECOS empty, as `useradd -k /dev/null` leaves it, git refused the guess already, a `chfn` would reopen it). jj has no such condition and no hooks, so `jj clone` and `jj init` (aliases in `jj/config.toml` over `jj util exec`) run `jj-identity`, which copies the three values git resolves into jj's per-repo config (`~/.config/jj/repos/<id>/config.toml`, keyed by `.jj/repo/config-id`; jj keeps it outside the repo since 0.38) and re-authors a fresh working-copy commit; `jj/config.toml` carries no `[user]` on purpose, so a repo set up any other way warns on every command and cannot push until `jj-identity` is run in it (`signing.key` stays global: an empty key makes gpg fail and would abort the clone at its first commit).

## Step 3 - Reboot

Power on → LUKS (YubiKey: FIDO2 PIN + touch; no key: passphrase after 30 s) → TTY1 runs `login` for your user (`getty@tty1` drop-in from `install.sh`; `LOGIN_TIMEOUT 0`, so an unattended prompt does not restart `login` every minute): touch the key while it blinks, or unplug it (or wait the ~29 s) and type the password at `Password:`. The cue says so, because the tty echoes while the token waits: a password typed then shows in clear and is discarded. No autologin, `login` authenticates every time → `zsh/.zprofile` execs Sway. TTY2 keeps the `login:` prompt and stays a shell. `sudo bootctl status` reads `Secure Boot: enabled (user)`, and its `Current Stub:` block ends in `/EFI/Linux/arch-linux.efi`: the firmware ran the UKI itself; `sbctl status` shows `Vendor Keys: none`.

## Security model

| State | Opens it | Notes |
| --- | --- | --- |
| Off, hibernated | YubiKey + FIDO2 PIN + touch, or the LUKS passphrase | Device and key together are not enough. Eight wrong PINs wipe the key's FIDO2 applet, the passphrase remains ([YUBIKEY.md](./YUBIKEY.md#recovery)). |
| Locked session (suspend included) | touch of a plugged YubiKey, or password | Touch without PIN is the walk-away trade-off; `idleSuspend` 3600 s → `suspend-then-hibernate`, `HibernateDelaySec=1h`, so an hour later the next wake is a LUKS unlock; a shut undocked lid sleeps at once, locked on the way down (lid policy under Lock and idle). faillock: three wrong passwords within 15 min close the password path for 10 min, the touch path stays open. Polkit requests that arrive while locked, or are still open when the lock engages, are cancelled by the shell (Polkit below). Not closed: a `sudo` issued by code running as the user while the screen is locked. The token serves requests one at a time in arrival order, each gets its own touch, and neither requester hears of the other (measured both ways with a background `sudo true`: asked 4.6 s after the lock's request, it waited through the unlocking touch, the key blinked on for it and the next touch ran it; asked 3.1 s before the lock engaged, the first touch at the lock screen ran it and left the screen locked, the second unlocked; neither side got an error or a timeout, the lock's hint stayed `Touch YubiKey or enter password` and its log holds no failure either way, so it cannot warn). The tell is a touch that does not do what you expected: the lock screen stays, or the key blinks on again right after the unlock. While the key blinks for a reason you do not know, the password is the safe answer, and no touch until the key goes dark: the queued request outlives the unlock and takes a touch after it. |
| `login` (any VT), `sudo`, polkit | touch, or password | `pam_u2f` `sufficient` in `/etc/pam.d/login`, `/etc/pam.d/sudo` and `/etc/pam.d/polkit-1` only. A machine left at the prompt with the key plugged in is the same walk-away trade-off as the locked session. Touch without PIN also means code already running as the user can call `sudo` or `pkexec` itself and wait for a touch: the key blinks, nothing on screen says who asked. The jailed programs cannot (`firecfg --list` names them; each jail hides `sudo`, `pkexec` and `su` through firejail's common blacklist or forbids new privileges, the browser's does both); unconfined code can, and inside sudo's ticket without even the blink: `timestamp_type=tty` (sudo's default; neither the stock `/etc/sudoers` nor the `%wheel` line in `/etc/sudoers.d/wheel` sets a timestamp option) keeps one record per terminal for `timestamp_timeout` 5 min after the last `sudo` on it (so any `sudo` inside the window renews it, which is all `yay`'s `sudoloop` does through a build), and a `sudo` from that terminal within the window runs without authenticating. faillock does not count the touch path, so a locked-out password still leaves the key. |
| `su`, ssh | password | Neither stack carries `pam_u2f` (`su` has its own, `sshd` uses `system-auth`). `sshd.service` ships with `openssh`, no script enables it; ufw drops inbound anyway. `systemd-ssh-generator` would still start `sshd-unix-local.socket` (AF_UNIX `/run/ssh-unix-local/socket`, local only) on every boot, so `install.sh` masks it. |

Boot path: the firmware runs only what the machine's db key signed, and that is the two UKIs (kernel, initramfs, microcode and command line in one signed image). Closed: a swapped or foreign UKI, an unsigned initrd or `.addon.efi` (the stub checks addons against db), a command line edit (no menu, no editor, and the stub ignores a command line passed in while Secure Boot is on), foreign boot media except the signed recovery stick (Recovery stick). Sidecars the stub still takes along unverified (`.cred`, `.sysext.raw`, `.confext.raw` next to the UKI or under `loader/`) are measured, not trusted: PID 1 files the credentials as untrusted, and this initramfs carries no sysext or confext at all. Someone with the device reads nothing from the LUKS volume and can no longer plant a boot change that runs at the owner's next unlock; the firmware setup sits behind the supervisor password. Open: the firmware itself (an implant, or the SMBIOS Type 11 string `io.systemd.stub.kernel-cmdline-extra`, which the stub appends to the command line whatever the Secure Boot state), DMA before the kernel has the IOMMU up, the running or suspended system (the LUKS key is in RAM), replay of an older UKI signed by the same key (no revocation: the key signs every rebuild and an old copy stays valid), a copy of the signed stick (its two signed files boot any ISO on this machine: a live system with the ESP and the hardware in front of it, not the LUKS volume; the stick gone missing is the Fresh keys bullet), and the Secure Boot keys themselves, which live in `/var/lib/sbctl` inside the encrypted root, so root on the running system can sign anything. A last item on that list is a lockout rather than a breach: with the keys gone (`/var/lib/sbctl` emptied) the `sbctl` hook prints `not signing!` and exits 0, pacman finishes a transaction whatever a post-transaction hook returns, and the next UKI lands unsigned, which the firmware refuses at boot; `qs-pkg update` ends with `sbctl verify` for that, a plain `pacman -Syu` relies on Recovery. Clipboard history is plaintext on disk (LUKS covers it). gpg-agent caches the on-disk GPG keys' passphrases for 7 days (`max-cache-ttl 604800`, step 17); the card asks its PIN on its own terms. Firejail confines the browser and a few tools (`firecfg --list`), nothing else: another browser gets its stock profile through the hook if `firecfg.config` names it (none of `librewolf.local`'s changes) and runs unconfined if not; the browser also carries AppArmor's `firejail-default` profile through `/etc/firejail/librewolf.local`, and `xdg-dbus-proxy` is what makes the profiles' session-bus filters real (without it firejail allows the whole bus, with only a warning on stderr). The jail talks to the whole `org.freedesktop.portal.Desktop` name, so `xdg-desktop-portal/sway-portals.conf` sets `DynamicLauncher` to `none`: a host app (the firejailed browser is one to the portal) installs launchers through it without a dialog and could overwrite `~/.local/share/applications/librewolf.desktop`, the file the launcher runs. tmux ignores a pane's OSC 52, write and query alike (`set-clipboard external`; its own copy-mode `y` still reaches kitty's clipboard, a program in a pane that sets the clipboard itself, nvim on a remote host say, no longer does), so what a pane prints cannot replace the paste or read it, with one gap: `allow-passthrough on` (yazi's image previews) lets a pane wrap an OSC 52 in a DCS that reaches kitty as is, and kitty takes writes without a prompt (`clipboard_control` default; reads it asks about), so a `cat` of a foreign file can still plant a paste.

## Desktop shell (Sway + Quickshell)

One Quickshell process owns everything, including the lock screen and the idle ladder (`swaylock` stays installed as the fallback, `swayidle` only bridges logind's Lock and sleep signals). `sway/config` and `tmux/tmux.conf` stay the single source of truth for keybindings - the launcher parses them live into the Keybindings menu (Sway · Tmux · Launcher · Popups), grouping `h/j/k/l` and `1-0` runs into one row and labelling commands from a table in `MenuModel.js`. Helper scripts live in `bin/` (→ `~/.local/bin`, prefix `qs-`, plus `yay-git`, `snap-restore` and `jj-identity`); launcher rows and panel buttons are data, `core/Commands.qml` turns them into processes (`argv`, `term` = kitty window, `task` = `qs-task` floating window that waits for Enter when done). Every interactive zsh execs into the tmux session `default` (`zsh/.zshrc`; a TTY2 login lands in the same session), except the floating terminal (`$mod+Shift+Return`, started with `NO_TMUX=1`). Floating kitty windows (`qs-float`, `qs-task`) take kitty's own size, 113x27 cells (`initial_window_width/height`, `remember_window_size no`), not a sway `resize set`: whole cells leave kitty no remainder to pad.

Battery state is one `core/Power` singleton shared by every output (one udev listener, one low-battery toast (its last level sits in `PersistentProperties`, so a config reload does not repeat it), one auto-profile write); it reads plugged/charging state from sysfs (`/sys/class/power_supply/AC/online`, `BAT*/status`) and re-reads on `udevadm monitor` power_supply events (plus one settle read 2 s later: the EC reports `Not charging` for ~1 s after a charge-limit write and resumes silently) and on UPower state changes - no polling - so plug/unplug shows instantly instead of after UPower's debounce (UPower still supplies %, time estimates). `qs-toggle nightlight` kills any stray `wlsunset` before starting/after stopping its own so one instance owns gamma on every output. Only periodic work in the shell: `core/Metrics` samples each resource on its own timer (net 2 s, cpu 3 s, gpu 5 s, ram 10 s, `df` 5 min) so the bar reads as independent tickers, `qs-weather` refreshes every 15 min (a failed fetch retries after 30 s, five times at most), the Network segment re-checks connectivity every 15 s while NM reports `limited` or `portal`, the Network popup samples rates every 1.5 s while open, and the clock ticks on `SystemClock`. Qt timers run on the monotonic clock and freeze across suspend/hibernate, so swayidle's `after-resume` calls `qs-shell shell resume`, which refetches weather, re-reads the clock in `core/Sun` and drops the stale net-rate sample.

Popups open from the keyboard tmux-style: `$mod+o` enters sway mode `popup`, the bar centre shows `POPUP  m media · a audio · n network · b battery · c calendar · w weather` (`panel/widgets/Mode.qml`, fed by `SwayState.mode`), the next key opens the popup and leaves the mode. `resize` mode shows the same way.

Workspaces: `1` and `4` live on the laptop panel, `2` and `3` on the first external output when one is present (sway moves them back out on plug-in, merges everything onto the laptop on unplug). `assign` rules send Slack → 1, kitty → 2, LibreWolf → 3, Zoom → 4; any other workspace is created on the focused output. Caps Lock is a second `$mod` (`caps:super`), so `Caps+N` switches workspaces one-handed. Touchpad: tap to click, `clickfinger` (two fingers right, three middle), `scroll_factor 0.4`. `for_window` floats LibreWolf's picture-in-picture (sticky, follows the workspace) and `xdg-desktop-portal-gtk` dialogs (a separate process without a parent, sway would tile them). The workspace segment shows a dot on unfocused workspaces that hold windows (from sway's `representation`) or are urgent. `core/SwayState` runs one `swaymsg -m -r -t subscribe '["window","mode","input"]'` and fans out binding mode, xkb layout and window changes (workspace occupancy refresh on new/close/move/floating only, fullscreen probe) - Quickshell's I3 module only forwards workspace/output events.

Notifications: popups stack top-right on the output that was focused when the first one arrived and stay there until the last is gone (4 visible, the rest wait hidden and start a full countdown when they surface, at most 20 in total: past that the oldest waiting one expires, critical included, it is in the history already, so a sender in a loop cannot pile up live objects and cards; `$mod+Shift+d` / `$mod+Shift+a` act on the newest card on screen, not on the last one queued; critical 10 s, others `min(expire, 10 s)`, default 5 s), history of 50 in `notifications.json`, `dnd` toggle. Summary and app name render as plain text; the body is Qt StyledText re-serialised by `notifications/Body.js`: only `b i u s em strong del p br` and `<a href="http(s)://...">` pass as tags, every other `<` becomes `&lt;` (Qt's parser aborts a malformed tag early and resumes mid-text, so a strip that mirrors its grammar can be fed a nested `<img>`; escaping everything unknown cannot), Chromium's page-origin prefix is dropped, links open only for `http(s)`, and every other foreign string renders as `PlainText` (`Label`, the glyph hint, the OSD's track title; Qt's default AutoText turns the first `<img>` into a fetch), so no sender can make the shell fetch a URL. History rows are cut (summary 512, body 4096) before `notifications.json` takes them; the live card cuts the body at 8192 before `Body.styled` walks it and drops a `qs-glyph` hint longer than 8 UTF-16 units (one glyph with its modifiers is shorter; D-Bus allows 128 MiB). `bin/qs-notify` escapes `& < >` in the body it sends: our toasts are text, and some of it is foreign (`qs-usb` relays udisksctl, whose mountpoint carries the stick's own label). A `replaces_id` update rewrites the live object without a second `onNotification`, so the card listens for summary/body/image changes, resets its countdown and re-snapshots the history row (once the toast has expired the id is gone from the server, so a later `-r` makes a new toast). The popups live in a `ListModel`, so a toast coming or going leaves the other countdowns alone. The countdown pauses while hovered and resumes with what was left; a pointer parked over a toast holds that toast only. sway 1.12 sends no `wl_pointer.enter` to a layer surface mapped under a stationary pointer, so `Stack.qml` maps a 1x1 transparent nudge layer on the first frame after a card appears and unmaps it 100 ms later: each map makes sway rebase the cursor against the drawn toast, which then reads as hovered. Left-click runs the default action (else the first), other buttons dismiss; the `qs-glyph` hint replaces the bell when there is no icon.

Lock and idle: `lock/Locker.qml` holds the `ext-session-lock` (`WlSessionLock`) and two `PamContext`s that run as the user: `qs-lock-password` (`pam_unix`; faillock tallies every wrong password (limits in the security model table); PAM's own notice shows in the status line. The tally file `/run/faillock/$USER` sits in a root-only directory the user-run stack cannot create in, so `lock_pam` installs a tmpfiles rule that creates it at boot, otherwise nothing would count until a `sudo` or polkit auth made the file; it is `0660 $USER root`, the mode pam_faillock itself uses so that a screensaver's stack can write it, which also lets anything running as the user clear its own strikes, `faillock --user $USER --reset` truncates the file: the lockout limits a person at the keyboard, not code in the session) and `qs-lock-u2f` (`pam_u2f`, touch only, no PIN; the mappings file is group-readable for that). Both PAM files come from `post-install.sh` step `lock_pam`; without the password one `lock()` falls back to a plain `swaylock` child, and `lock status` reports `fallback` for it and `foreign` for a swaylock the shell did not start (both count as locked for the focus gating below). Engaging: `qs-lock` (sway `$mod+Escape`, also `--locked`), the launcher's `Lock` row, the idle ladder, `swayidle lock 'qs-lock'` on logind's Lock signal (`loginctl lock-session`), or `swayidle before-sleep 'qs-lock --sleep'` (the lid's sleep included; `lock sleep` IPC, which first pauses every MPRIS player that can pause, a stream without MPRIS plays on; then polls `lock status` for `"secure":true` for 3 s, then starts swaylock and gives it the last second of a 4 s budget under logind's 5 s delay, then `output * power off`: the kernel thaws every device to write the hibernation image and i915 restores what was lit, so the lock screen would otherwise come back for the seconds the write takes; `swayidle after-resume` runs `output * power on` first). A lock made for sleep starts no touch request until `after-resume`'s `qs-shell -q shell resume`, and a session locked earlier with a request in flight (idle lock, key blinking, then the lid) drops a touch that lands between the sleep call and the freeze, about 0.5 s measured, since it would have put an unlocked session to sleep. systemd-sleep freezes the session within the second and the token sleeps with the bus (LED off until the wake); after a plain suspend the request in flight survives and the next touch completes it, after a hibernation (the laptop was off) the token is a new device and the request dies; `resume` rescans the token and the touch path starts once udev has made the node readable. The flag `$XDG_RUNTIME_DIR/qs/locked` is written before the lock is requested and emptied after unlock, so a shell crash, `qs-session restart` or a config reload re-locks on startup (sway keeps the session locked with a red screen in between; `$mod+Escape` re-locks by hand; `FileView` preloads asynchronously even with `blockLoading`, so the check reads `text()`, never `loaded`, before a job was awaited). State lives in `core/Lock` (`locked` = our request; the compositor's confirmation is read from `WlSessionLock.secure` inside `Locker`; never bind on `WlSessionLock.locked`, quickshell never emits its change on unlock). While locked, the launcher, popups and polkit prompt drop keyboard focus and stay closed (sway 1.12 lets exclusive layer surfaces take focus from the lock surface; fixed in sway master). The lock screen: blurred wallpaper, clock, one password field mirrored across outputs (`Esc`/`Ctrl+U` clear), `Enter` submits; with a FIDO token present (`udevadm` `ID_FIDO_TOKEN`, watched while locked) `pam_u2f` runs concurrently and a touch unlocks; a failed attempt (token not readable yet, not enrolled; one holding an earlier assertion queues the request instead, Security model) re-arms after 1.5 s on the first instant failure, 3 s on the second, 5 s from then on (750 ms after a slow one) and never stops, the hint reads `YubiKey not ready, retrying` meanwhile and `YubiKey not accepted, still retrying` after six instant failures. A pending touch is never aborted: a SIGKILLed `pam_u2f` leaves the token holding that assertion until its own ~29 s timeout and the next touch would go to it, so a password unlock leaves the child waiting (a lock within that window reuses it) and the child's result is ignored once unlocked. The child's run time is wall clock, so a sleep in between shows up in the log as a run of many hours. The field stays editable during the 2 s rejection delay (`Enter` is ignored until the check ends), and a badge names the xkb layout when it is not the first one. `lockBlank` (10 s, `0` disables) idle seconds while locked power the outputs off and clear the field; the key press that wakes them is swallowed (100 ms, plus that key's auto-repeats while it stays held), and sway's `input added` burst after a VT switch back relights outputs the stored `power off` would keep dark. `qs log` carries `lock:` lines (engaged, u2f attempt/result, password rejected, unlocked by); `lock status` adds `u2fActive`, `u2fAttempts`, `u2fFast`, `sleeping`. Idle ladder (`lock/Idle.qml`, `IdleMonitor`s on `ext-idle-notify`, compositor-timed so suspend cannot skew them): `idleScreensaver` 900 s → `qs-screensaver start` (`cmatrix` in a fullscreen kitty per output), `idleLock` 1800 s → lock (which also stops the screensaver), `idleSuspend` 3600 s → `systemctl suspend-then-hibernate`; `0` disables a rung. The `awake` toggle is an `IdleInhibitor` on the wallpaper layer (always mapped; a hidden bar would not count) - `systemd-inhibit --what=idle` never reached swayidle. Lid: logind owns the switch (step `lid`). Shut and undocked → `suspend-then-hibernate` at once, so `swayidle before-sleep` pauses the players, locks, holds the touch path and darkens the outputs on the way down; undocked, the key never starts blinking behind a shut lid, and the hibernation hour counts from the close. Docked (an external connector that is connected and enabled in sway, or a dock reporting its switch) → nothing, the idle ladder alone applies. logind re-checks the rule after every event while the lid stays shut (`button_recheck`): undocking a shut laptop sleeps it right then, and a close within `HoldoffTimeoutSec` (30 s after boot or wake) is acted on when the holdoff ends. The `awake` toggle holds the idle ladder, not the lid; `qs-pkg update` holds both (`systemd-inhibit --what=sleep:handle-lid-switch`, the lid skips plain sleep inhibitors by `LidSwitchIgnoreInhibited=yes`) and logind sleeps a lid still shut the moment the upgrade ends. Works at a tty and with the shell dead alike. sway only folds the panel away (`bindswitch --reload --locked lid:on output eDP-1 disable`, `lid:off` enables it again): a shut docked laptop runs clamshell on the external display, workspaces 1 and 4 move there and come home on open (the `workspace N output` assignments), undocked the panel is off for the second before sleep and back on wake, and `--reload` re-applies the state on a config reload. No `unlock` IPC exists on purpose; `lock status` never includes typed text. `qs-session` runs quickshell under its own supervisor (`QS_DISABLE_CRASH_HANDLER=1`, relaunch unless three deaths within 60 s, then it gives up behind `qs-lock`, which is `swaylock` with no shell to answer: no shell means no idle ladder, and a lock that died is a red screen without a prompt; `$XDG_RUNTIME_DIR/qs/supervise.pid` names its process group so `stop`/`restart` take supervisor, shell and child processes down together; before relaunching it kills the dead instance's leftover children, since a PAM fork or `wl-paste --watch` still holding the old D-Bus sockets stops the new shell from registering the notification server and the polkit agent, which quickshell never retries).

Polkit: `polkit/Agent.qml` registers a `PolkitAgent` at `/org/qs/PolkitAgent` and shows one card on the focused output (scrim, exclusive keyboard focus). The message loses polkit's preamble (`Authentication is required to run \`x' as the super user` → `Run x as the super user`), the identity line names the user. PAM runs its modules one after another, so the password field only exists while PAM asks for text; the rest of the time the same box shows a pulsing status with PAM's own words (`Touch the YubiKey, or unplug it and type the password` while `pam_u2f` runs first, about 29 s until the token gives up and the password prompt follows; `Checking` after a submit). When the field is shown it has focus and a click lands in it; while it is hidden a `FocusScope` around the card holds the keyboard, so `Esc` cancels at any point (footer says `Esc cancel` or `Esc cancel · Enter submit`). A touch does authenticate `pkexec`: the `pam-u2f` package relaxes the helper's sandbox (`polkit-agent-helper@.service.d/pam-u2f.conf`, `DeviceAllow=char-hidraw`). Cancelling is not free: polkit only closes the helper's socket, PAM runs on, `pam_unix` fails its conversation ~29 s later and faillock counts a strike, the same as a wrong password (`faillock --user $USER` shows them). The agent pays that price while the screen is locked: PAM starts the moment a request arrives, so a request hidden behind the lock would sit in `pam_u2f` waiting for a touch nothing on screen named, and the touch at the lock screen would approve it. Requests arriving while locked, and one still open when the lock engages, are cancelled (`qs log`: `polkit: request while locked, cancelling <action>`, `polkit: lock engaged, cancelling <action>`), the caller gets `Request dismissed`. The helper still runs its PAM stack to the end: untouched, `pam_unix` fails its conversation when `pam_u2f` gives up and faillock counts the strike; touched, the touch is eaten (`No session for cookie` in the journal, the lock then needs a second one) and nothing is authorized either way. A process in the session can burn strikes this way, which closes the password path for 10 min at a time, never the touch path. PAM info lines show below the field only when they arrived with the prompt or during it (faillock's lockout notice); the touch cue from the phase before is not repeated there, since quickshell never clears `supplementaryMessage`. A wrong password shakes the card, borders it red and says `Authentication failed` while polkit starts the next attempt from the touch phase. `qs-shell polkit status` → `{registered, active, responseRequired}`.

Reboot required: `core/System.qml` watches `/run/reboot-required` (written by the pacman hook `zz-reboot-required.hook` for kernels/systemd/glibc/mesa/firmware/…, installed by `post-install.sh` step `pacman_hooks`). No polling, no notification: shows ↻ in Indicators and a yellow dot on `Packages`/`Update`/`Reboot` rows until reboot (`/run` is tmpfs). `kernel-modules-hook` keeps the running kernel's modules through the upgrade (USB storage, exfat, a new dongle still load), so a missing `/usr/lib/modules/$(uname -r)` is not a signal; `linux-modules-cleanup.service` moves the copy to `/usr/lib/modules/.old` on the next boot, tmpfiles deletes it after four weeks.

Packages: `install.sh` turns on `Color`, `VerbosePkgLists` (the package list as a table: name, old → new version, size) and `ILoveCandy` in `/etc/pacman.conf`, nothing else. The mirrorlist is the ISO's copy of `pacman-mirrorlist` (`pacstrap` without `-M`): every mirror on, the Worldwide CDNs first by file order, so pacman tries them first and falls through on failure. The package's own file ships with every `Server` commented out, so each `pacman-mirrorlist` release lands a `mirrorlist.pacnew`; the pacnew row shows it, `r` keeps the list. Measured 2026-10 from a Ukrainian line on `extra.db`, `geo.mirror.pkgbuild.com` 27 MB/s, `fastly.mirror.pkgbuild.com` 19, the best Ukrainian mirror 23 and the rest 8-16, so a `reflector` ranking buys nothing and costs a timer. `qs-pkg update` prints Arch news newer than the newest installed package first (`yay -Pw`; manual interventions are announced there and nowhere else), then `yay -Syu`. The hook `zz-orphans.hook` lists orphans (`pacman -Qdtq`) after every transaction, in the same terminal. yay reads `yay/config.json` (→ `~/.config/yay`, four keys, the rest stay yay's defaults): `sudoloop` keeps the sudo timestamp alive through a long build, so one YubiKey touch covers the install at the end instead of a second prompt blinking at an empty chair; `cleanAfter` deletes the downloaded sources once the package is in (`git clean -fx --exclude '*.pkg.*'` in the clone: 1.1 GB of brave, zoom, slack and 1password archives sat under `~/.cache/yay`, next to 1.8 GB of built packages it would have kept, hence `PKGDEST` on the tmpfs; a downgrade is `snap-restore` or a rebuild from the AUR git history); `removemake` drops make dependencies after the build; `batchinstall` builds everything first and installs in one pacman transaction. Pacnew: `zz-pacnew.hook` runs `pacdiff -o` after any transaction that touched `/etc` and writes the list to `/var/lib/pacnew-pending` (not `/run`: the files outlive a reboot; printed in the upgrade terminal too); `core/System.qml` watches it, `Packages` shows `N pacnew to merge` with the yellow dot (a pending reboot outranks it) and the row `Merge pacnew files` lists them, dimmed when there are none. The row runs `qs-pkg pacdiff`: `pacdiff --sudo` as the user, so each pair opens in `nvim -d` with the user's config through `sudoedit` and only the file moves run as root, then the list is rebuilt. Two edges: a file in a directory the user cannot enter is skipped by pacdiff (the row warns, `sudo pacdiff` merges it), and `sudoedit` refuses a symlinked target such as `/etc/resolv.conf` (→ the resolved stub), so answer `r` there, never `o`, which would replace the link with a file. A `pacdiff` run by hand leaves the list stale until the next transaction. The hook knows the backup files of installed packages, so a `.pacsave` left by a removed package never shows (`qs-pkg remove` uses `-Rns`: none created). Code from outside pacman and the AUR: the zsh and tmux plugins. `zsh/.zshrc` clones antidote from GitHub (`--depth 1`) at the first shell start and `antidote bundle` clones the seven repositories of `zsh/.zplugins` the same way; `tmux/tmux.conf` clones TPM at the first tmux start and TPM its three plugins (`tmux-fzf`, `tmux-resurrect`, `tmux-continuum`; `git clone --single-branch --recursive`); each lands at whatever its default branch's HEAD was that moment, no commit pinned, and nothing here updates them (`antidote update` and `prefix + U` by hand). nvim's plugins are pinned by `nvim/nvim-pack-lock.json`, Mason's tools are not (nvim/README.md); yazi's plugin and flavour are vendored, `yazi/package.toml` pins their revisions.

Network share: the `smb` step makes `~/nas` an automount, not a mount. The `.automount` is what boot enables, so nothing waits for the NAS at boot or login; the first `cd ~/nas` mounts (with the NAS unreachable the kernel gives the connect up after 5 s, measured 5-6 s against a dead address and a dropped SYN, 0.3 s when refused: `ls` gets an error, the next access tries again), five idle minutes unmount again (`TimeoutIdleSec=300`), so sleep and lid usually find nothing mounted and the next access starts clean. While something holds it (yazi in the directory) the kernel cifs client reconnects by itself after a Wi-Fi drop or a NAS reboot, `soft` being its default. Measured with the share held open and every packet to the NAS dropped: the first `ls` blocks for three echo intervals before `soft` gives it an error, 187 s at the default `echo_interval=60`, 50 s with `echo_interval=15` (`CIFS: VFS: \\nas has not responded in 45 seconds. Reconnecting...`), hence the option; a further access while the NAS is still gone fails in 10 s, the first one after it is back takes 1 s and the mount is whole again. `LazyUnmount=yes`: `systemctl stop` on that busy, unreachable mount returned in 0.0 s (a shutdown would otherwise wait on it), the automount had it back in 0.1 s. `uid`/`gid` map the files to the user, `file_mode=0644` keeps eza and yazi from painting every file executable. SMB version negotiates (3.1.1 with any current NAS), no `seal`: the LAN is trusted here as for plain HTTP. The password goes `LoadCredential=` → `credentials=%d/...`, so `systemctl cat` and `ps` show a path only. Edges: `stat` on the directory is free (`ls -l ~` does not mount) but fzf's built-in walker behind `Ctrl-T`/`Alt-C` (and `fd` behind `**<Tab>`) in `~` descends into it and triggers the mount, with the NAS away that thread waits those 5 s; a second share is another `--redo smb` with another path; removal is `systemctl disable --now <unit>.automount`, `systemctl stop <unit>.mount`, `rm` the two units and the credstore file, `daemon-reload`.

Power: kernel and `power-profiles-daemon` defaults, no TLP, no tunables. Measured 2026-10 on the T480 at idle on battery (panel at 36 %, 60 s medians of `BAT1/power_now`; ±0.05 W inside a minute, a few tenths of drift between minutes, so only back-to-back pairs compare). A static screen (one tiled window, nothing redrawing) draws 4.3 W. The knobs were stacked one after another against a 5.3 W baseline (a terminal redrawing, the bar still spinning, next paragraph): `kernel.nmi_watchdog=0`, runtime PM for the Ethernet controller (it does reach D3 with the cable out), for the Wi-Fi card and its root port, for the AHCI controller, USB autosuspend for the SD reader (never idles: the kernel polls it for a card every 2 s, `events_dfl_poll_msecs`) and the Bluetooth radio blocked (its own pair, 5.37 vs 5.39). The medians ran 5.27 to 5.36 with no step down at any knob, so none is worth more than the drift. PCIe ASPM cannot be set at all: the FADT declares no ASPM support and the kernel disables it (`pcie_aspm.policy` refuses writes). The usual checklist buys nothing measurable on this machine; what is on already (`powersave` governor with EPP `power`, `mem_sleep` deep, Wi-Fi power save, `snd_hda_intel power_save=10`, SATA `med_power_with_dipm`) is the kernel's and ppd's doing.

Idle CPU: with nothing changing on screen quickshell sits at 0.5 %, sway at 0, the GPU in rc6 throughout (`/sys/class/drm/card*/gt/gt0/rc6_residency_ms`). The trap, for the next animation: a QML animation inside a hidden window keeps running (item `visible` does not know the window is unmapped), and once a tiled window covers the wallpaper sway stops sending it frame callbacks; the next time it draws under cover (a reload, a wallpaper change) Qt marks that window unexposed and, left with one exposed window, advances every running animation from the bar's vsync, so the bar repaints 60 times a second with nothing new to draw. The polkit card's waiting pulse did that until 2026-10 (12 % quickshell, 8 % sway, GPU out of rc6 27 % of the time, 0.15 to 0.4 W between paired minutes, all on a static screen). Rule: an always-on animation is gated on its window, `running: win.visible && ...`; a `Behavior` only runs on a change and is fine. The lock surface is the same picture from the other side: the bar stays mapped under it and goes unexposed at its next clock tick, so `ui/Marquee` (a long title in Media) also stops while `Lock.locked` or while its window is hidden (bar hidden, fullscreen), a track change included (a `Timer.restart()` overrides the `running` binding, so the re-arm on new text checks the same condition), or the lock surface would repaint at 60 Hz for every scroll.

Reload: `swaymsg reload` typed in a terminal prints a run of empty prompts, `$mod+Shift+c` does not. The reload runs inside sway's event loop, so the Enter release waits in libinput behind it, and a Wayland client on `wl_seat` v9 repeats a held key itself after `repeat_delay`: kitty keeps sending Enter until the release arrives (sway #5379, open since 2020; #4975 was the bound-key variant, fixed). The official fix is `wl_keyboard` v10 (Wayland 1.24): the compositor sends `repeat_info` rate 0 and emits the repeats, so a blocked compositor emits none. kitty 0.49 implements the client side, wlroots 0.20 still advertises v9. Why the block is long: it is CPU-bound in libxkbcommon (`perf`, 2026-10). sway 1.12 compiles a keymap with a fresh `xkb_context` once per `input` line for validation (even touchpad lines) and parses the config twice per reload (validation, then the real pass), resets every keyboard to defaults, reconfigures each of the 5 keyboard devices (`AT Translated Set 2 keyboard`, `ThinkPad Extra Buttons`, `Sleep Button`, `Power Button`, `Video Bus`) once per seat pass and once more for `input type:keyboard`, and serialises the keymap twice for every `wlr_keyboard_keymaps_match` and `wlr_keyboard_set_keymap`: 47 compiles and some 40 serialisations for a config that did not change. `seat seat0 fallback true` is what sway synthesizes when no seat is named; stated, `load_main_config` skips its own fallback pass instead of applying the same seat config twice, 37 compiles (900 to 690 ms on battery, where power-saver holds the CPU at 800 to 900 MHz; 270 to 200 ms plugged in, which is `repeat_delay`, so a typed reload there prints one empty prompt at most). The rest is sway's, so reload with `$mod+Shift+c`: a bind consumes the press and the terminal never sees the key.

## Recovery

- Boots, but broken since an update: `snap-restore` lists the snapshots (it re-runs itself under `sudo`); `snap-restore last` (also the launcher's System → Roll back last update) swaps `@` for the snap-pac `pre` snapshot of the last pacman run, rebuilds both UKIs inside it (kernel on the ESP = modules in the root) and offers the reboot. `snap-restore N` for any other snapshot. The replaced root stays as `@_replaced`, with its disk space, until the next restore deletes it; `snap-restore undo` swaps it back (one level, not a history). Not `snapper rollback` (openSUSE layout).
- The kernel does not boot: F12 at power-on → `Arch Linux LTS` (the UKI at `EFI/BOOT/BOOTX64.EFI`; the firmware's own disk entry lands there too, so it boots with the NVRAM entries gone), then `snap-restore last`. Covers a kernel regression only: both UKIs share the initramfs config and rebuild in the same transaction.
- Nothing boots: live ISO (from the signed stick below with Secure Boot on; a plain ISO stick is unsigned: F1 → Security → Secure Boot → Off for that boot, On again afterwards) → `cryptsetup open /dev/<luks-partition> cryptroot` → `mount -o subvol=@home /dev/mapper/cryptroot /mnt` → `/mnt/<user>/projects/dotfiles/bin/snap-restore --device /dev/mapper/cryptroot list`, then `last` or `N` (same script; `arch-chroot` is on the ISO). `rebuild` instead only rebuilds the UKIs from the current `@` (broken initramfs, root fine; also the way out when a restore's own rebuild failed). With Secure Boot on, `snap-restore` refuses a root whose `/var/lib/sbctl` key is not the one in the firmware's db (older than the keys, or from before a re-key): the UKIs it would rebuild could not boot. With Secure Boot off it restores anything; `sbctl verify` in the restored system before turning it back on.
- `Secure Boot Violation` for both UKIs after a BIOS reset or flash, or an install that ran outside Setup Mode and Secure Boot switched On since: the firmware does not hold the keys. F1 → Security → Secure Boot → Reset to Setup Mode, boot (Setup Mode verifies nothing), `sudo sbctl enroll-keys -i`, reboot. sbctl refuses when the TPM event log shows an option ROM (a discrete GPU, some NICs: firmware the key would lock out; none here): `-i --tpm-eventlog` puts those ROMs' hashes into db next to the key, still no Microsoft CA. The keys live in `/var/lib/sbctl/keys`, inside root snapshots like everything else, nowhere else; the supervisor password is the one thing to keep.
- BIOS update: Lenovo's bootable image is not signed by this machine's key, so Secure Boot Off for that boot, On again after, then `sbctl status` (`Setup Mode: Disabled`, `Secure Boot: Enabled`; a flash that dropped the keys is the bullet above).
- Fresh keys (the db key has signed something it should not have, the signed stick is lost, or `install.sh` warned that keys or signatures failed): F1 → Reset to Setup Mode (not needed when the firmware never left it), then `sudo rm -rf /var/lib/sbctl/keys && sudo sbctl create-keys && sudo mkinitcpio -P && sudo sbctl enroll-keys -i` - a rebuild, not `sbctl sign-all`, which would append a second signature to the already signed UKIs. Snapshots from before the re-key then need Secure Boot off to restore (above); a kept stick gets its second partition written and signed again (Recovery stick, the `xz -dc` line through `umount`), not a fourth signature on top.
- LUKS header damaged (no keyslot opens, `cryptsetup luksDump` fails): live ISO, `cryptsetup luksHeaderRestore /dev/<luks-partition> --header-backup-file <usb>/luks-header-YYYYMMDD-HHMM.img` from the step 5 USB; keyslots revert to that date.
- Neither key unlocks: boot without key, passphrase (keyslot 0) after 30 s. FIDO2 PIN blocked or applet wiped → [YUBIKEY.md](./YUBIKEY.md#recovery).
- Red screen, no lock prompt (shell died while locked and the relaunched one did not re-lock; after the third death within 60 s the supervisor runs `qs-lock` itself, so `swaylock` holds the screen; once unlocked, `qs-session start` from a terminal brings the shell back, `restart` would re-lock from the flag): `$mod+Escape` re-locks (bound `--locked`), or from another VT `WAYLAND_DISPLAY=wayland-1 SWAYSOCK=$(ls /run/user/1000/sway-ipc.*) qs-session restart`, which re-locks from the flag. Lock screen itself broken: from the VT `qs-session stop`, then `WAYLAND_DISPLAY=wayland-1 swaylock` (replaces the abandoned lock), unlock on the sway VT, fix, `qs-session start` (drops the stale flag; `restart` would re-lock).
- Lock prompt refuses a correct password: usually faillock (three wrong tries within 15 min close the password path for 10 min; the status line shows PAM's notice): wait, unlock with the YubiKey, or `faillock --user $USER --reset` as root. A broken `/etc/pam.d/qs-lock-password` → `post-install.sh --redo lock_pam` (when the file is missing the shell answers `lock` with `fallback` and starts `swaylock` instead).

## Recovery stick

A plain ISO stick needs Secure Boot off for its boot (above). A Ventoy stick signed once with the machine's db key boots with Secure Boot on and takes any ISO as a file copy, no rewrite. Ventoy's chain: `EFI/BOOT/BOOTX64.EFI` is shim as Microsoft signed it (CA 2011 and 2023, neither in this db, so it gets this machine's signature as a third) → `EFI/BOOT/fbx64.efi` is Ventoy's loader, Ventoy-signed; Ventoy's stock flow enrolls Ventoy's certificate into MOK through MokManager at the first boot, here the file carries this machine's signature too, shim finds it in db and MokManager is never used → `grubx64_real.efi` is GRUB, which the loader checks by hash (`Ventoy hash check failed.` and a warm reset when the file changes, so the firmware starts over from the top of `BootOrder` and a one-shot F12 pick is gone: do not sign it) → the ISO, unverified, as on every Ventoy stick. The stick is a key, not a filter: whoever holds it boots anything on this machine (Security model). `sbctl sign` without `-s`, so the stick is not in sbctl's file list and the pacman hook never looks for it.

Tested with `ventoy-1.1.18-linux.tar.gz` (sha256 `d86ff9de63d94c8b8f1f6b14d23c55af4b88e8207bf2893890892a6a97b1ad54`). The installer's `xzcat | dd bs=512 count=N` for the 32 MiB `VTOYEFI` partition reads a pipe without `iflag=fullblock` and can come up short (137 kB on this run, the tail of the filesystem: only `ventoy/vtoyutil_*.efi` live there, so the stock stick boots regardless); the second partition is written again from the decompressed image and compared, then signed:

```sh
echo 'd86ff9de63d94c8b8f1f6b14d23c55af4b88e8207bf2893890892a6a97b1ad54  ventoy-1.1.18-linux.tar.gz' | sha256sum -c
tar xf ventoy-1.1.18-linux.tar.gz && cd ventoy-1.1.18
sudo sh Ventoy2Disk.sh -i -g /dev/sdX                    # GPT; Secure Boot support is the default
xz -dc ventoy/ventoy.disk.img.xz > /tmp/vtoyefi.img
sudo dd if=/tmp/vtoyefi.img of=/dev/sdX2 bs=1M conv=fsync
sudo cmp /dev/sdX2 /tmp/vtoyefi.img                      # silent = identical
sudo mount /dev/sdX2 /mnt
sudo sbctl sign /mnt/EFI/BOOT/BOOTX64.EFI
sudo sbctl sign /mnt/EFI/BOOT/fbx64.efi
sudo sbctl --disable-landlock verify /mnt/EFI/BOOT/BOOTX64.EFI /mnt/EFI/BOOT/fbx64.efi   # ✓ signed; landlock confines verify to the ESP
sudo umount /mnt
udisksctl mount -b /dev/sdX1 && cp ../archlinux-x86_64.iso /run/media/$USER/Ventoy/ && udisksctl unmount -b /dev/sdX1
```

F12 → the USB entry → Ventoy's menu → the ISO. `Ventoy2Disk.sh -u` (a Ventoy update) rewrites the second partition: the `xz -dc` line through `umount` again, from the new version's directory; the ISOs on the first partition stay.
